Imagine a Great Apps customer who buys a new phone, transfers the apps and only notices at the next login: the authenticator app didn't come along. The old phone is still in the drawer, working. They want to do the obvious thing, which is to point 2FA at the new device. Without a dedicated path for that, the only way out would be to disable 2FA and enable it again, which leaves the account without a second factor precisely at the moment it's most exposed.

## The problem

Great Apps' 2FA is a small service on a Cloudflare Worker, based on TOTP: the six-digit code the authenticator app generates from a shared secret and the current time, changing every 30 seconds. The service generated the secret, showed the QR code, confirmed activation and verified the code at login.

Two real-life flows were missing: switching devices while holding the old one, and recovering access with a backup code when the old device is lost.

## Why it wasn't trivial

Changing the second factor is an authentication operation. Everything that protects login has to protect the change as well, against someone who already has the password. In practice, there were four concrete problems:

- the change can't invalidate the current device before the new one proves it works, otherwise the customer locks themselves out in the middle of the process;
- the attempt limit has to withstand parallel requests. A "read counter, add one, write" loses counts when ten requests arrive together;
- an accepted TOTP code can't be reused within the window in which it's still valid;
- the TOTP secret and the backup codes can't be readable in the database.

## The solution

### Pending secret

The change requires a code from the current device. With that validated, I generate a new secret and new backup codes and keep both as pending. Login only reads the active secret, so the pending one never authenticates anyone. Only the confirmation, with a code generated by the new device, promotes the pending one to active. If the customer gives up halfway, the old device keeps working as always.

Recovery through a backup code uses the same design. The backup code is consumed, the new secret stays pending, and the old one only stops being valid when the new one is confirmed.

### Attempts reserved before verification

Each attempt is reserved before the code is checked, with an `UPDATE` conditioned on the counter and on the row version I read. If two requests read the same counter, only one manages to write. The one that reaches the fifth failure writes the 15-minute lockout in the same statement. Only a success resets the counter.

Whoever loses the race gets an explicit conflict error. The server doesn't retry on its own, and a conflict doesn't count as an attempt, but it doesn't verify the code either. That way there's no path in which a parallel burst tests more codes than the limit allows.

### Single-use code

The time step of the accepted code is written to the row with another conditional `UPDATE`: it only passes if the step is greater than the last one used. If no row was affected, the code was already used and the response says exactly that. Since verification accepts a window of one step on each side, to tolerate a phone clock that's off, this lock is what stops the same code from being valid twice within those 90 seconds.

### Secrets at rest

The TOTP secret is now encrypted with AES-GCM, and the backup codes are stored as HMAC-SHA256 with a pepper (an extra secret key, kept outside the database). The keys live in Cloudflare's Secrets Store, outside the code and outside the database. Since records in the old format already existed, I kept reading both formats during the transition and wrote a batch migration that uses the same per-row compare-and-set. A row changed between the read and the write is skipped and left for the next pass. Once the transition is over, the migration and the old reading leave the code.

### Notices and per-IP limit

A completed change, a used recovery, a lockout from attempts and a deactivation all trigger an email to the account holder. Code verification also now shares the per-IP limiter with login, so there's no second door without a ceiling.

## An example

The attempt reservation, in SQL with generic names:

```sql
-- $2 is the counter I read, $3 the row version I read
UPDATE two_factor
SET failed_attempts = $2 + 1,
    locked_until = CASE WHEN ($2 + 1) % 5 = 0
                        THEN now() + interval '15 minutes'
                        ELSE locked_until END,
    version = version + 1
WHERE user_id = $1
  AND failed_attempts = $2
  AND version = $3
  AND (locked_until IS NULL OR locked_until < now())
RETURNING failed_attempts, locked_until;
```

Now an attacker with the password firing six codes in parallel, all reading the counter at 3:

| Request | Read | Reservation result | Code verified? |
|---|---|---|---|
| 1 | 3 | writes 4 | yes, wrong |
| 2 to 6 | 3 | zero rows, conflict | no |
| 7 (new read) | 4 | writes 5 and locks for 15 min | yes, wrong |
| 8 | 5 | blocked before reserving | no |

Without the conditional reservation, all six would have read 3, written 4 and verified six different codes, spending a single attempt of the limit.

And the device change, step by step:

1. `t=0` customer sends the old phone's code, the new secret stays pending;
2. `t=20s` new QR code scanned on the new phone;
3. `t=35s` customer sends the new phone's code, pending becomes active, notice email goes out;
4. if step 3 never happens, the old phone remains valid.

## Result

Device change and recovery now work with no window in which the account has no second factor or is open to brute force. The scenarios of concurrent bursts, a reused code, lockout and format migration are covered by automated tests. The design and the threat model are documented alongside the code, so whoever touches it later understands why each lock exists.

## What I take from it

An authentication flow with state should be written as conditional transitions in the database, not as in-memory logic. The condition in the `WHERE` is the only thing that stays true when ten requests arrive in the same millisecond.

And every credential change needs a pending state that authenticates nothing until it's proven. That's what lets the customer make a mistake, give up or lose the connection halfway without locking themselves out.
